## 附：`VERSION` 已改说明

`VERSION` 从 `v0.20.0`（上游版本号）改为 `v0.1.0`。

**为什么必须改**：`use-version-check.ts` 会把本地版本与远端 `VERSION` 比较，判断「是否有新版本」。若沿用 `v0.20.0`，我们的头几个版本号都低于它，永远不会提示更新；而且会给用户一种「这个项目已经迭代 20 个大版本」的错觉。

**注意**：`web/vite.config.ts` 直接读根目录 `VERSION` 注入 `__APP_VERSION__`，改完需重新构建才生效。

## 附二：仓库是 private，版本检查暂时无法生效（2026-11-20 实测）

### 事实

`Supenman/INTX` 目前是 **私有仓库**（GitHub search API 返回 `"private": true`）。因此：

| 访问方式 | 结果 |
|---|---|
| `raw.githubusercontent.com/Supenman/INTX/dev/VERSION` | **404** |
| `cdn.jsdelivr.net/gh/Supenman/INTX@dev/VERSION` | **404** |
| GitHub MCP `get_file_contents`（带授权） | 200，内容 `v0.20.0` |
| 对照：其他公开仓库的 raw 文件 | 200 |

### 结论

- 这不是代码 bug，也不是沙箱网络问题（同环境访问别的仓库 raw 正常）。
- `use-version-check.ts` 的「检查更新」在仓库转公开前**一定失败**，失败时静默回退到本地版本，用户只会看到「已是最新」。
- 曾经尝试加 jsDelivr 兜底，实测同样 404，已回退——不留无效代码。

### 前置条件（按顺序）

1. 把仓库转公开，或
2. 把 `VERSION` / `CHANGELOG.md` 发布到能公开访问的地方（自有域名 / GitHub Pages / npm registry 的 `dist-tags`），再改 `REPO_RAW` 指向它

### 顺带发现

远端 `VERSION` 仍是 `v0.20.0`，本地已改为 `v0.1.0`，但**这一轮还没推上去**。转公开前必须让两边一致，否则转公开当天所有用户会看到「发现 v0.20.0 新版本」的假提示。

### 验收

仓库转公开后，在浏览器打开 `https://raw.githubusercontent.com/Supenman/INTX/dev/VERSION` 应返回 `v0.1.0`。

## 附三：npm 包这条在本机走不通（2026-11-21 实测）

### 实测

| 检查 | 结果 |
|---|---|
| `registry.npmjs.org/@basketikun/canvas-agent` | **200**，上游包存在 |
| `registry.npmjs.org/-/user/supenman` | **404**，账号不存在 |
| `search?text=scope:supenman` | `total: 0`，该 scope 下无任何包 |
| `~/.npmrc` 里是否有 token | 无 |

### 结论

这条**不是代码问题，是账号问题**：

1. `supenman` 这个 npm 账号根本不存在，`@supenman` scope 也从未被占用
2. `@intx` 大概率同样没占（未逐一验证，但同理由）
3. 没有 npm 发布凭证，本机无法 `npm publish`

按清单原定顺序「先发布成功、再改前端常量」——**第一步就卡住**，所以前端常量保持 `@basketikun/*` 不动。

### 为什么故意不改代码「先占位」

改了但不发布，用户复制到的命令会变成 `npx -y @supenman/canvas-agent@latest`，执行后 npm 返回 404。**现在这条命令至少是能跑的**（装的是上游包）。用一个 404 换掉一个能跑的命令，是倒退。

### 解锁条件（需要人来办，不是代码）

1. 注册 npm 账号（用户名决定 scope，例如注册 `intx-studio` 就得到 `@intx-studio`）
2. `npm login` 或写 `~/.npmrc` 的 `//registry.npmjs.org/:_authToken=xxx`
3. 回来跑：`cd canvas-agent && npm publish --access public`
4. 发布成功拿到 200 后，再改这三处：
   - `web/src/components/agent/agent-connect-view.tsx:36` 的 `command`
   - `web/src/stores/use-config-store.ts:93` 的 `LOCAL_PROXY_PACKAGE`
   - `canvas-agent/package.json` 的 `name` / `repository` / `author` / `homepage`
5. 验收：干净环境 `npx -y <新包名>@latest --version` 有版本号输出

> `canvas-proxy` 的源码不在本地工作副本里（在远端仓库），发布前要先拉下来。

### 一句话

**这条我改不了，因为缺的不是代码是账号。** 强行改只会更糟。

### 以后怎么发

新增 `.github/workflows/publish-npm.yml`，走 **Trusted Publishing（OIDC）**：

- job 里 `id-token: write`，npm 用 GitHub 签发的短期身份换一次性发布权限
- **不存任何 token**，凭据随 job 失效
- 只在 `release: published` 或手动触发时跑，不在每次 push 时跑

版本号规则：

```
Release tag = canvas-agent-v0.6.1  →  发 canvas-agent，且校验 tag 与 package.json 一致
Release tag = canvas-proxy-v0.1.1  →  发 canvas-proxy
tag 与 package.json 对不上          →  直接失败
```

**为什么校验 tag**：tag 是外部可见的版本声明，package.json 是实际发出去的东西。
两者不一致时发出去的包会让人装到一个名字对、内容不对的版本，比失败更难排查。

### 还需要做的一步（一次性，在网页上）

到 https://www.npmjs.com/package/@supenman/canvas-agent/access 绑定 Trusted Publisher：

| 字段 | 值 |
|---|---|
| Publisher | GitHub Actions |
| Organization or user | `Supenman` |
| Repository | `INTX` |
| Workflow filename | `publish-npm.yml` |
| Environment | 留空 |

两个包分别绑一次（`canvas-proxy` 同理）。

### 为什么必须改

npm 已把 classic token 全部永久吊销（2025-11 截止），现在只有 Granular。
而 Granular 里带 bypass 2FA 的直接发布权限，**2027 年 1 月起移除**，
之后只能「暂存 + 人工批准」。Trusted Publishing 是官方推荐的替代路径，
现在接上就不用再经历一次迁移。
