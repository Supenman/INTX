# INTX 从当前版本到成熟项目实施计划

> 版本：v0.1 规划版  
> 目标：将 INTX 从“已有画布与生成闭环的可运行原型”推进为“个人本地长期可用的 AI 创作工作台”。  
> 原则：先体验、再可靠性、后能力扩展；优先复用现有实现和成熟依赖，避免重复造轮子。

---

## 1. 项目定位

INTX 最终定位为一个**以无限画布为核心的本地 AI 创作工作台**：

> 整理素材 → 编写提示词与分镜 → 配置生成参数 → 生成图片/视频 → 对比与筛选 → 继续创作 → 导出和归档

成熟项目不等于功能数量最多，而是满足以下标准：

- 用户不看源码也知道下一步怎么做。
- 界面显示的功能都有真实可验证的执行链路。
- 任务失败、取消、重试和结果保存的边界清楚。
- 项目、资产和生成结果不会因为刷新、重启或异常退出而轻易丢失。
- 新增模型、节点和工具时，不需要修改大量无关代码。
- 安装后能运行，出现问题时能诊断、恢复和导出信息。

---

## 2. 当前基线

### 2.1 已有基础

当前项目已经具备继续产品化的基础：

- React + TypeScript + Vite 前端。
- React Flow 无限画布。
- Zustand + Immer 状态管理。
- Tauri 桌面封装。
- 文字、素材、生成、分镜宫格节点。
- 节点连线、选择、框选、复制、删除、撤销、重做、整理。
- Mock 与 OpenAI 兼容适配器。
- 生成任务状态、取消、失败分类和部分结果补齐。
- 资产哈希去重、预览、裁切、蒙版和项目导入导出。
- 自动保存、启动恢复、审计台账和复现包。
- 节点注册表、工具注册表和运行时适配边界。
- 单元测试、浏览器 E2E、生产构建和 Rust 检查。

### 2.2 当前不足

当前仍属于“功能基础已成形、产品体验尚未成熟”的阶段：

- UI 规则和工作台信息层级尚未完全统一。
- 常用节点参数的编辑入口仍需完善。
- 画布、素材库、设置和审计之间的关系还可以更清晰。
- 多项目管理和桌面文件存储需要进一步实机验证。
- 真实视频生成链路尚未形成完整闭环。
- 结果历史、版本比较和模板复用能力不足。
- 助手、插件和本地推理属于后续能力，不应提前扩大范围。
- Windows 安装、升级、备份、恢复和长期运行还需要产品级验证。

### 2.3 当前质量基线

每一阶段都必须保持以下基线：

- 类型检查通过。
- ESLint 通过。
- 单元测试全部通过。
- 结构预算通过。
- 浏览器 E2E 全部通过。
- 生产构建通过。
- 涉及桌面能力时，追加 Tauri 实机验证。

测试数量和文件数量只代表覆盖规模，不代表功能自动完成；每个新能力必须有对应的用户流程验收。

---

## 3. 总体路线

按以下顺序推进：

1. **UI 与交互基础**：让已有功能好找、好懂、好操作。
2. **图片与分镜创作闭环**：把最核心的本地创作流程做可靠。
3. **项目与数据可靠性**：让用户敢长期保存真实作品。
4. **视频生成与交付**：接通一个真实视频渠道，完成结果落盘。
5. **创作效率与复用**：模板、历史、搜索、批量操作。
6. **桌面产品化**：安装、升级、性能、诊断、备份和长期运行。
7. **按需智能化**：助手、插件、本地推理和云能力。

这不是一次性开发清单。每阶段完成并验证后，再根据真实使用痛点决定下一阶段细节。

# 4. 阶段一：UI 与交互基础

## 目标

让用户可以不依赖开发者说明，完成：

> 新建画布 → 添加节点 → 编辑参数 → 连接素材 → 执行生成 → 查看结果 → 保存和恢复

## 4.1 统一视觉基础

建立一套稳定的 UI 规则，避免每个面板各自设计：

- 背景、面板、边框、正文、辅助文字、强调色。
- 字体大小和信息层级。
- 间距、圆角、控件高度和阴影。
- 普通、悬停、聚焦、禁用、成功、警告、错误状态。
- 按钮、输入框、下拉框、弹窗、菜单、提示的统一样式。
- 键盘焦点和可访问名称。
- 空状态、加载状态和失败状态的统一表达。

先完成当前暗色主题；样式使用集中式 CSS 变量，为以后增加浅色主题保留空间，但不在此阶段同时扩大范围。

## 4.2 稳定工作台布局

将界面明确分成几个职责区域：

| 区域 | 职责 |
|---|---|
| 顶部项目栏 | 项目名称、保存状态、撤销重做、导入导出 |
| 创建工具区 | 添加节点、导入素材、常用动作 |
| 中央画布 | 节点、连线、选择和产物组织 |
| 侧边或浮动面板 | 资产、任务、设置、审计和参数详情 |
| 画布控制区 | 缩放、适应全部、适应选择、小地图 |

原则：高频操作可见，低频功能按需展开；不把所有功能常驻在屏幕上，也不把关键操作全部隐藏在多层菜单内。

## 4.3 节点卡片交互

统一四类节点卡片的结构：

1. 类型和标题。
2. 输入来源与连接状态。
3. 高频参数。
4. 提示词或素材内容。
5. 产物预览。
6. 当前任务状态与操作按钮。

参数交互规则：

- 常用参数直接在卡片内编辑。
- 参数定义、选项和默认值只有一个来源。
- 参数变更不自动触发生成。
- 已有产物不因为改参数而丢失。
- 任务排队或执行中锁定会影响当前任务的参数。
- 任务失败或结束后恢复编辑。
- 参数修改进入已有撤销/重做历史。
- 复杂或低频参数保留在详情面板，不强行塞入卡片。

## 4.4 画布交互

按优先级完成：

- 空白、单节点、多节点三类右键菜单。
- 节点从工具区拖入画布。
- 素材从素材库拖入画布。
- 选择、框选、多选、复制、粘贴、删除语义统一。
- 快捷键说明面板。
- 缩放到 100%、适应全部、适应选择。
- 连线过程中的可连接/不可连接反馈。
- 更容易点击的连接热区。
- 节点预览、分镜预览和返回画布。

## 4.5 反馈与空状态

建立以下反馈层级：

- 短暂成功：轻量提示。
- 当前节点错误：保留在节点内。
- 需要用户处理：显示明确动作和原因。
- 高风险动作：确认后执行。
- 任务进行中：显示阶段和取消入口。
- 尚未实现的能力：隐藏或明确标记，不能伪装成可用功能。

## 阶段一验收

- 新用户可以完成一条完整 Mock 创作流程。
- 参数编辑、画布拖拽、快捷键和菜单不会互相误触。
- 节点卡片、素材库、设置和审计的打开/关闭行为一致。
- 失败信息包含原因和下一步动作。
- 原有自动化测试不回归，新增交互均有 E2E 覆盖。
- 不以“增加了多少按钮”作为完成标准，以完整用户流程作为完成标准。

# 5. 阶段二：图片与分镜成熟闭环

## 目标

先把图片和分镜做成真正可使用、可恢复、可交付的核心流程，不同时展开所有媒体类型。

## 5.1 模型和渠道配置

- 明确当前渠道支持的媒体类型和参数。
- 配置页面显示能力，而不是让用户盲选无效组合。
- 连接测试区分地址、凭据、协议、模型和网络问题。
- 渠道配置不进入项目包。
- 错误提示不泄漏凭据。

## 5.2 生成任务体验

任务状态统一区分：

- 准备输入。
- 提交请求。
- 上游生成。
- 下载结果。
- 写入本地资产。
- 完成、失败、取消或提交不确定。

必须遵守：

- 没有真实百分比时不显示虚假进度。
- 提交不确定不能静默重发。
- 本地取消不等于上游已取消。
- 保存失败不等于生成失败。
- 已经拿到的结果不能因为同批另一项失败而丢失。

## 5.3 分镜体验

- 明确文本如何拆成分格。
- 支持逐格查看和逐格另存。
- 部分失败保留已成功格。
- 重发只补缺失格。
- 修改宫格参数后，明确区分“新任务”和“旧任务补齐”。
- 产物记录使用稳定的任务和输出身份，避免串图。

## 5.4 结果管理

- 记录生成参数、输入资产、模型和时间。
- 允许选择主结果。
- 支持结果预览、下载和重新放回画布。
- 支持分镜拼图导出。
- 支持完整项目包导出。

## 阶段二验收

至少选定一个真实图片渠道，完成：

> 文本与参考素材 → 图片生成 → 分镜生成 → 部分失败 → 补齐 → 预览 → 导出 → 刷新恢复

Mock 适配器继续用于自动化测试，但 Mock 通过不能替代真实渠道验收。

---

# 6. 阶段三：项目与数据可靠性

## 目标

让用户可以把真实项目长期放在 INTX 里，能够保存、恢复、备份和迁移。

## 6.1 多项目

- 新建项目。
- 打开、重命名、复制和归档项目。
- 最近项目列表。
- 项目封面或摘要。
- 项目切换时处理未保存状态。
- 项目之间的节点、素材、任务明确隔离。

沿用现有项目仓库接口，不重新建设第二套持久化系统。

## 6.2 保存和恢复

- 显示保存中、已保存和保存失败。
- 异常退出后恢复最后一致快照。
- 写入过程尽量避免半成品覆盖正式数据。
- 缺少部分资产时给出可理解的诊断。
- 未完成任务恢复时区分“继续查询”“重新下载”和“重新生成”。

## 6.3 备份与迁移

- 用户可以导出完整项目包。
- 导出包可在另一环境导入。
- 项目格式有版本号和迁移逻辑。
- 导入前先校验，失败不覆盖原项目。
- 升级前提供备份建议或自动备份。
- 旧版本数据保留迁移报告。

## 6.4 素材库

- 按类型、来源、时间和引用关系筛选。
- 区分“从画布移除”和“删除资产文件”。
- 删除前显示引用位置。
- 清理未使用资产前先预览。
- 大图和视频采用按需加载，控制内存。

## 阶段三验收

需要实际验证：

- 强制退出后重开。
- 保存失败或目录不可写。
- 部分资产缺失。
- 旧格式导入。
- 多项目切换。
- 导出后重新导入。
- 运行中任务重启后的状态恢复。

# 7. 阶段四：视频生成与交付闭环

## 目标

不是增加一个“视频”选项，而是真正完成一个视频文件的生成、查询、下载、保存和预览。

## 首个视频范围

先选择一个真实渠道和一种流程，例如图生视频：

1. 输入图片和提示词。
2. 选择渠道支持的时长、比例和模型。
3. 提交并保存上游任务身份。
4. 轮询或恢复查询状态。
5. 下载结果。
6. 写入本地资产库。
7. 预览、下载和放回画布。

## 必须处理的异常

- 应用重启后继续查询。
- 查询成功但下载失败。
- 临时下载地址失效。
- 大文件断点或重新下载。
- 下载失败不能重新购买生成。
- 本地取消不承诺上游已取消或退款。
- 模型参数不支持时，在提交前阻止。
- 视频文件损坏时给出恢复入口。

## 暂不做

- 完整非线性编辑器。
- 多轨时间线。
- 复杂特效、调色和音频混剪。
- 自建转码系统。
- 多渠道智能路由平台。

先使用成熟媒体工具完成必要的预览和基础处理，逐项核对许可证和打包成本。

## 阶段四验收

完成：

> 分镜图片 → 视频生成 → 重启后继续查询 → 下载失败恢复 → 本地播放 → 导出

---

# 8. 阶段五：创作效率与复用

## 目标

让用户第二次创作明显比第一次更快。

## 建设内容

- 常用节点组合保存为模板。
- 提示词片段和参数预设。
- 项目内搜索和节点定位。
- 产物历史、版本选择和前后对比。
- 批量生成、批量下载和批量标记。
- 任务列表按状态、项目和时间筛选。
- 失败任务集中处理。
- 快速复制项目或局部创作片段。

## 约束

- 模板先以项目内模板为主，不先做模板市场。
- 批量操作必须明确任务边界，避免重复提交。
- 版本和产物身份必须稳定，不能用文件名猜关系。
- 复杂功能必须从实际使用频率中产生，不为“看起来完整”预建平台。

## 阶段五验收

用户能够：

- 从已有模板快速创建新项目。
- 找到历史结果并进行比较。
- 批量处理多个明确选中的节点或资产。
- 失败后只处理失败项，不重复成功项。

# 9. 阶段六：桌面产品化与稳定版

## 目标

从“开发环境可运行”变成“安装后可长期使用”。

## 9.1 安装与升级

- Windows 安装包。
- 首次启动。
- 默认目录和权限提示。
- 升级流程。
- 卸载流程。
- 升级前数据保护。
- 版本和变更说明。
- 可复现的打包环境。

## 9.2 性能

以真实项目建立基线：

- 节点数量。
- 素材数量和总大小。
- 图片与视频预览数量。
- 长时间运行任务数。
- 启动和项目打开时间。

优化顺序：

1. 先测量。
2. 找到实际瓶颈。
3. 优先利用 React Flow 和浏览器已有能力。
4. 只在有数据证明时增加索引、虚拟化或缓存。
5. 优化后补充回归场景。

## 9.3 凭据与诊断

- 评估桌面端凭据存储方案。
- 项目包、任务日志和诊断信息脱敏。
- 提供可复制的诊断摘要。
- 错误包含阶段、模型、任务身份和建议动作，但不包含密钥。
- 真实请求、费用和隐私边界在设置中明确说明。

## 9.4 文档

- 五分钟入门。
- 画布基础操作。
- 模型配置。
- 项目保存和备份。
- 导入导出。
- 常见错误恢复。
- 数据位置和隐私说明。
- 当前已实现与未实现能力清单。

## 阶段六验收

在干净的 Windows 环境完成：

> 安装 → 配置 → 创作 → 保存 → 关闭 → 重开 → 升级 → 数据继续可用

同时完成真实项目的稳定性和性能验证。

# 10. 后续可选能力

以下能力不进入当前主线，只有出现真实需求后再评估：

| 能力 | 进入条件 |
|---|---|
| AI 创作助手 | 业务用例、权限和写入边界已经稳定 |
| 插件系统 | 现有节点/工具注册机制无法满足多个真实扩展需求 |
| 本地 AI 超分 | 模型、硬件、资源、许可证和打包方案明确 |
| macOS / Linux 支持 | Windows 主线稳定且有实际用户需求 |
| 云同步 | 本地项目格式、冲突策略和备份机制可靠 |
| 多人协作 | 确认有真实协作场景和同步需求 |
| 对外发布或商业化 | 完成许可证、隐私、凭据和交付审核 |

成熟的个人本地工具不必拥有所有平台化能力。

---

# 11. 避免重复造轮子的规则

所有新需求按以下顺序判断：

> **INTX 已有实现 → 现有依赖 → 成熟上游库 → BeefTV 行为参考 → 最小自研实现**

每项需求记录：

- 用户问题。
- INTX 当前已有能力。
- 可复用的函数、组件、状态或依赖。
- BeefTV 仅提供的行为参考。
- 为什么需要新增代码。
- 具体调用入口。
- 正常、失败、取消和恢复验收场景。

必须遵守：

1. 不维护两套参数定义。
2. 不维护两套任务状态判断。
3. 不为了一个渠道预建复杂路由平台。
4. 不为了几个工具预建插件市场。
5. 不复制完整参考项目架构。
6. 不把占位按钮当作已完成能力。
7. 不在没有真实调用点时添加抽象层。
8. 不以搬入代码文件数量作为进度。

# 12. 版本里程碑

| 里程碑 | 完成定义 |
|---|---|
| 体验版 | 画布、节点、参数、素材和反馈交互统一，核心流程易用 |
| 图片创作版 | 至少一个真实图片渠道和分镜流程完整可恢复 |
| 可靠工作区版 | 多项目、保存恢复、备份迁移和素材引用可信 |
| 视频创作版 | 至少一个真实视频渠道完成生成、查询、下载和导出 |
| 效率增强版 | 模板、历史、搜索和批量处理真正提升效率 |
| 1.0 稳定版 | 安装升级、数据安全、诊断、性能和文档达到长期使用标准 |

每个里程碑必须有可运行的端到端流程，不能只以代码合并或界面数量作为完成标准。

# 13. 当前执行顺序

当前立即执行的顺序：

1. 收尾节点参数编辑控件，并补齐端到端测试。
2. 统一节点卡片、空状态、任务状态和错误反馈。
3. 整理工作台布局和面板打开/关闭行为。
4. 完善画布右键菜单、拖拽、快捷键和视图控制。
5. 完成一轮 UI 体验验收。
6. 再进入真实图片与分镜闭环加固。
7. 完成数据可靠性后，再开始视频生成。

本计划不预设具体工期。每一阶段先定义范围、实现、验证和回归结果，再决定下一阶段；不在基础体验和数据可靠性未稳定前并行展开视频、助手、插件和云能力。
