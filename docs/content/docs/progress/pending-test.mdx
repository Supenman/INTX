# Pending Tests

The current release needs manual verification in these areas:

## Canvas agent: three permission levels and paid-action confirmation (pending user verification)

- The permission menu at the bottom-right of the agent composer existed but was never wired up. It now works, and all three levels — `Ask for approval`, `Automatic review`, `Full access` — apply to canvas operations.
- `Automatic review` (default): canvas edits run directly, while **paid generation and deletions still show a confirmation card**. `Ask for approval`: every non-read-only change needs a click. `Full access`: even paid generation runs without asking (the menu shows this in orange). Read-only operations (viewport moves, selection changes) never prompt in any level.
- The confirmation card reports only what matters: how many actions cost money (with an estimate; when a channel has no unit price it says "no unit price configured" instead of showing 0), how many deletes, how many other edits. Confirming **replays only the pending operations**, so already-applied nodes are not added twice and no order is placed twice; both halves of a batch share one undo snapshot, so a single undo reverts the whole batch.
- The level is stored in `localStorage` under `infinite-canvas:agent-permission` and survives reloads and canvas switches.
- Automated: typecheck, 50 files / 711 cases, domain boundary check, production build and the three-viewport overflow check pass. 25 new cases (`agent-permissions.test.ts` — 20 pinning the three-level table and that confirmation replays only the pending part; `agent-permission-persist.test.ts` — 5 pinning the default, stale-value fallback and that a failed write still applies in-session), all checked destructively (reverting the replay list to "all" turns 3 cases red; dropping the stale-value guard turns the fallback case red).
- **Verified in browser**: the three menu entries and their descriptions render, picking `Ask for approval` updates the label, `localStorage` gets `request`, `Full access` survives a reload, and the dropdown stays inside the viewport at both 1440 and 390.
- **Not verified**: a real `run_generation` confirmation card driven by a connected local agent (needs a local agent and a real key; no provider request was sent this round), and the cost estimate against an actual charge (depends on the channel unit price).

## Channel egress mode: local proxy / direct (pending user verification)

- The channel editor drawer gains an "Egress" segmented control below the API key: `Follow local proxy` (default) and `Direct to upstream`.
- `Follow local proxy` behaves exactly as before: the global proxy switch decides whether requests are rewritten to the `127.0.0.1` proxy prefix.
- `Direct to upstream` stops routing this channel through the local proxy — the URL is left alone even when the global proxy switch is on.
- Scope: ModelScope async submit and polling, upstream image download, re-checking failed tasks in the task centre, and the OpenAI-compatible URL builder all read the same switch.
- No migration needed: a channel without a `proxyMode` field normalizes to `system`, so behaviour is unchanged.
- Automated: `web` typecheck, 47 files / 679 cases (13 new: 6 for normalization, direct not rewriting, system following the global switch and request-config pass-through; 7 wiring and failure-injection cases reached through `requestSingleImage`, see next bullet), domain boundary check and production build all pass.
- **Wiring and failure injection are pinned** (`web/src/services/api/image.test.ts`): the tests enter through `requestSingleImage`, the function the canvas node actually calls, and only fake the transport layer so the real branches in `image.ts` run — endpoint detection (channel protocol says openai but the host is ModelScope, still async), `proxyMode` taken from the channel, the three failure paths (401 / cancelled after submit / 2xx without a task id), and that the ledger never contains the token or the base URL.
- **These cases were checked destructively**: calling `createModelScopeTransport(requestConfig.proxyMode)` without the argument makes "egress mode follows the channel" fail immediately; restoring it turns everything green. "Green" alone was not accepted as proof.
- **Verified in browser**: on the config page, the control renders full-width under the API key, defaults to `Follow local proxy`, and the hint text switches when selecting `Direct to upstream`; console shows no errors.
- **Not verified**: an actual request with `Direct to upstream` (needs a real key on real hardware; no provider request was sent this round), and the switch's real effect on desktop (the Rust side has no CORS, so both values should be equivalent).
- **Known limitation (state it in the acceptance expectation)**: in a browser, choosing `Direct to upstream` for ModelScope is stopped at the CORS preflight (the preflight does not allow `X-ModelScope-Async-Mode`), so nothing is sent and nothing is billed — but the node shows "possibly submitted (no reply)". The control's hint says this; for case C1 treat "fails as expected but bills nothing" as a pass.

- Gemini 请求应带 aspectRatio（所选比例）；分辨率选了 1K / 2K / 4K 时应按尺寸表带上 imageConfig.imageSize，选自动时不带。质量不参与分辨率换算，视频尺寸设置保持原有行为。
- 图像质量可选自动与 5 档（低 / 中 / 高 / 极高 / 最高），请求里的 quality 字段应与所选档位一致，且尺寸不随质量变化。
- ModelScope 渠道的图像设置：选中接口地址为 api-inference.modelscope.cn 的渠道后，面板应显示「只接收模型与提示词」的说明，质量 / 尺寸 / 分辨率 / 宽高比 / 透明背景置灰不可操作；张数保持可用（逐张提交、每张单独计费）；切回其他渠道后应恢复完整设置。
- Gemini 渠道的图像设置：质量与透明背景应置灰，尺寸 / 分辨率 / 宽高比仍可选并照常参与请求；面板顶部的说明只列出真正不发送的项。
- 画布图像设置按钮的折叠摘要：ModelScope 渠道只显示张数，Gemini 渠道显示尺寸和张数，都不再显示质量；OpenAI 兼容渠道保持「质量 · 尺寸 · 张数」。
- 多张生成：画布一次选 N 张、工作台张数选 N，都应逐张提交，每张独立成败；人为让其中一张失败时，其他张仍应正常出图，失败的那张只标自己失败。
- 单图操作（遮罩、角度、节点重试、配置面板单张）只应产生一次单图请求，不应因为画布默认张数是 3 而多请求并丢弃多余结果。
- 取消语义回归：提交后取消（已拿到上游任务号）仍应判「可能已提交」，需要用户确认后才能重发；提交前取消才能直接重发。
- 待核实任务（设置 → 待核实任务）：ModelScope 出图后取图失败、或查单期间关掉页面，重开应用后这条任务应仍在列表里并显示任务号、模型和原因。
  - 配好 ModelScope 渠道后点「查单」，若上游已完成应取回图片、提示已存入「我的素材」，任务从列表中消失；若上游还在跑应提示稍后再查，任务仍在列表里。
  - 没配 ModelScope 渠道时，「查单」应禁用并提示先配置渠道；其余任务只能复制任务号去厂商后台核对。
  - 视频任务在列表里点「查单」应能续查原任务号；插件视频重启后已失效时，应提示失效而不是重新提交。
  - 整个过程不应产生任何新的提交请求（网络面板里只有查询 GET），也不应出现「重发」按钮。

## INTX 2.2a-1：任务异步存储（待用户验收）

- 任务台账仍使用当前 IndexedDB 的 `app_state` 和原任务键；首次读取当前 JSON 快照不改写，首次成功写入补版本元数据，既有任务/顺序/引用保留，不删除旧库。
- 提交前 task create、running 保存完成才进入厂商调用；保存失败提示尚未提交，不能自动改用 localStorage 或重新发请求。等待保存期间取消也应阻止提交。
- 上游返回任务号后先等待保存，再开始查单；若此时本地写入失败，设置 → 待核实任务应显示尚未保存的证据和任务号，允许复制与「重试本地保存」，不允许重新提交。
- 「重试本地保存」只写已知任务快照，不发网络请求；版本冲突显式报错，不能用旧任务覆盖新版本。
- 台账读取失败/损坏/未知格式应显示错误而非「没有任务」，支持重新读取；IndexedDB 无记录但检测到原 localStorage 回退键时阻止读写，不能静默导入或清空。
- 查单取回后任务记录保存失败，不提前显示恢复成功；已知产物引用保留在当前进程，可补记，不重新买图。
- **边界**：未保存的证据仅留在当前进程，崩溃后可能丢失，不能承诺重启一定找回。项目/素材 store 仍是原实现，跨素材与任务的保存屏障和崩溃补齐属于 2.2a-2/3、2.2c。
- 自动化验证与真机验收分开：类型检查、34 个测试文件/499 个用例、构建和 domain 依赖边界已通过；独立 fake IndexedDB 库覆盖并发冲突、晚阶段 abort、现有格式接入及读写失败。构建仍提示本机 Node 20.18 低于 Vite 要求，以及原有打包体积/混合导入警告。浏览器/Tauri 实际刷新恢复、保存失败界面及真实厂商查单尚未验证。故障点验使用独立测试库，不清空用户库；真实厂商请求须另行明确授权。
